# IT access-request requirements specification

Draft derived from `CHALLENGE.md`, `docs/requirements.md`, `materials/office-policy.md` and `snapshot.schema.json`; the supplied request exports provide examples, not additional policy.

Each numbered row contains one testable requirement sentence, its exact source words and a proposed check. Source sections use the documents' headings; schema sections use JSON pointers. Multiple quoted fragments are separate exact excerpts, not a rewritten quotation.

Checks are a verification proposal, not implemented tests or observed results. `tests/test_acceptance.py` and its named test methods are proposed locations, using the repository's existing unittest runner; these names do not prescribe the application's language, architecture or interface. Every test command runs from the repository root, and must report at least one selected test to count as verification. Inspection commands expose the named files; the comparison stated beside each command still requires review. Commands described as documented are to be supplied by the implementation's README, rather than invented here. Submission checks describe final hand-in obligations and do not authorize publishing this draft.

## Open Questions

These are the 10 highest-impact unresolved decisions for a production pipeline, prioritized by the risk of lost work, stale or inconsistent records, blocked recovery and incorrect routing. Related questions are consolidated; the requirements above remain unchanged.

1. **OQ-01 — Which revision wins?** When exports arrive out of order or concurrent attempts finish in reverse order, does “latest” mean export time, intake order or completion order? What prevents an older attempt from replacing a newer source or its error?

   **Production impact:** Reviewers could act on obsolete access details while the queue appears current. Sources: `docs/requirements.md` §§ Shared operations, Updates and follow-up; R-54, R-57, R-60.

   #### Findings

   The requirements mandate the latest processed source and latest-attempt error visibility, but neither the policy nor the supplied exports establishes how concurrent or out-of-order revisions are ordered.

2. **OQ-02 — What concurrency must be supported?** Are overlapping operators on one host, separate processes or separate regional machines? Must duplicate processing be prevented, or only duplicate publication, and may overlapping intake wait or be rejected?

   **Production impact:** An unsuitable coordination mechanism could cause lost updates, duplicate provider calls or corrupted history. Sources: `docs/requirements.md` § Shared operations; `materials/office-policy.md` § Processing and recovery; R-49, R-60.

   #### Findings

   The requirements explicitly anticipate overlapping operators and coherent shared records, but leave deployment scope, coordination behavior and duplicate-call prevention unspecified.

3. **OQ-03 — When are results durable and mutually consistent?** Must queue and extraction records agree during publication and after an abrupt crash, or only after a completed operation? What recorded state allows unfinished work to resume if the process dies between receiving a model response and saving its result?

   **Production impact:** A crash could lose completed work, leave jobs permanently running or expose a queue entry linked to the wrong extraction version. Sources: `docs/requirements.md` §§ Shared operations, Service interruptions and handover; R-61–R-63, R-90–R-91.

   #### Findings

   The requirements demand resumable recorded state and matching queue/extraction versions, but no persistence design defines the durable completion point or crash guarantees, and Python file replacement alone does not establish a transaction across both outputs.

4. **OQ-04 — How are outages bounded and retries controlled?** What timeouts, retry limits, backoff and rate-limit behavior apply? Does an unchanged rerun reuse an error or retry it, and does an explicit retry use the failed source/settings or the latest ones?

   **Production impact:** Requests could remain stuck, retries could overwhelm shared model capacity, or recovery could silently process different inputs. Sources: `docs/requirements.md` §§ Service interruptions and handover, Record and review behavior; `materials/office-policy.md` § Processing and recovery; R-44–R-48, R-63.

   #### Findings

   The policy requires visible failures, reproducible retries and preservation of earlier successes, but no selected provider or pipeline configuration defines timeouts, backoff, error reuse or which source/settings a retry uses.

5. **OQ-05 — What changes invalidate cached results?** Which prompt, schema, model, configuration, code and policy changes require refresh? Must a routing-only change rerun extraction, and how are affected records discovered and tied to the versions used?

   **Production impact:** A deployment could retain stale routing or trigger unnecessary model calls across the entire intake. Sources: `docs/requirements.md` §§ Updates and follow-up, Record and review behavior; R-48, R-58–R-59.

   #### Findings

   The requirements establish reuse for unchanged source/settings and refresh with configuration/policy provenance when behavior changes, but do not enumerate cache dependencies or distinguish rerouting from re-extraction.

6. **OQ-06 — What constitutes a valid, uniquely identified input?** Does filename identity include a path, and how are duplicate basenames handled? Which export versions and fields are accepted, and what per-document outcome is recorded for malformed JSON, invalid encoding or a missing/non-string message?

   **Production impact:** Unrelated documents could overwrite each other, while malformed exports could disappear from tracking or disrupt a batch. Sources: `materials/office-policy.md` §§ Input export format, Extracted facts, Processing and recovery; R-03–R-06, R-34, R-44.

   #### Findings

   The policy specifies UTF-8 JSON, a message string, filename identity and original-byte hashing, while examples use export version 1.0 and starter checks leave filename collisions, version compatibility and production handling of invalid inputs undefined.

7. **OQ-07 — What do operators see while work is pending?** During a refresh, is the old result displayed with a stale label, replaced by a pending entry or shown alongside it? Which states and output fields distinguish queued, running, retrying and interrupted work from completed results?

   **Production impact:** Reviewers could mistake stale results for refreshed ones, or operators could fail to locate work that needs recovery. Sources: `CHALLENGE.md` §§ The task, What to submit; `docs/requirements.md` §§ Updates and follow-up, Service interruptions and handover; R-02, R-55, R-61–R-63, R-90–R-91.

   #### Findings

   The brief requires completed results to remain inspectable and unfinished work to be distinguishable, but defines neither pending-state output fields nor how an older result is displayed during refresh.

8. **OQ-08 — What validation blocks publication?** Beyond JSON/schema validity and provider completion status, which checks must reject impossible dates, empty required values, fabricated quotes or unsupported facts? Should these become extraction errors or null fields with clarification issues, and may malformed model output be repaired automatically?

   **Production impact:** Structurally valid but unusable facts could enter the review queue, or recoverable data issues could cause repeated extraction failures.
