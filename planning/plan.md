# IT access-request build plan

## 1. Choices

- **Runtime:** Python 3.11+ with SQLite and a pinned dependency lockfile; this fits the existing unittest runner and supplies durable transactions without a separate database service.
- **Interface:** A CLI with intake, queue, progress, history, retry, resume, refresh, export and accuracy operations; operators on one shared host use the same database and can inspect committed work while workers continue.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests`; all tests use temporary state, saved responses or a fake transport, deny external network access, and must report a nonzero test count.
- **Model provider:** A configurable HTTP JSON adapter behind an injected provider interface, initially targeting an OpenAI-compatible chat-completions contract; send policy/prompt instructions separately from message data, request schema-constrained JSON where supported, and validate the returned envelope and extraction locally. Mock mode is the development default; live mode reads only `API_KEY` for credentials and requires explicit endpoint/model configuration.

This document plans future work only. No application, test, mock fixture, lockfile or deliverable is created in this planning step. All tests and commands below are proposed, not observed runs. Test names in the spec were proposals; the case IDs here replace them with one owning build step per test. Implementation must document an exact supported provider endpoint/model/request configuration and its transport contract; mocked transport checks exercise the real adapter without a live account or key.

### Operating decisions where the sources leave a choice

A key determination: “If the main files don't mention a solution or expected behavior, use the simplest scenario that still supports production operations.” The following decisions resolve OQ-01–OQ-10 from the spec for this implementation. They are design assumptions, not additional office policy.

| Question | Chosen behavior and limit |
| --- | --- |
| OQ-01: latest revision | Assign a monotonically increasing revision at durable intake acceptance for each filename. Export timestamps never decide ordering. A later accepted revision supersedes an earlier one; only the current revision's latest scheduled attempt can publish current results. Late completions remain in history. An old export deliberately submitted later counts as a new revision: upstream chronological reconciliation is outside this scope. |
| OQ-02: shared operation | Support multiple CLI processes on one host using one local SQLite database with transactional claims, uniqueness constraints and bounded lock waits. Use short transactions and never hold a database write lock during a provider call. Regional operators access this shared host; network filesystems and independent regional databases are unsupported. Duplicate publication is prevented; a crash after a remote call may cause a duplicate call on recovery. |
| OQ-03: durability and consistency | Save source bytes/settings and pending work before calling the model. Commit an attempt, its history and the current-result pointer together. Queue and extraction views join the same committed attempt in one read transaction. A received response is complete only after this commit. A crash before commit leaves recoverable unfinished work. Export immutable generations from one database snapshot and atomically replace a manifest pointer; snapshot readers resolve it once for both files. Final deliverables copy one verified generation. |
| OQ-04: failures and retries | Default to four workers, a configurable 60-second total attempt timeout, and at most three provider calls per attempt for transient network/429/5xx failures. Use capped exponential backoff with jitter, honor a valid Retry-After within a configured maximum, and release worker capacity while waiting. Exhaustion publishes an error. Do not automatically retry refusal, incomplete output or invalid JSON/schema. An unchanged intake reuses a terminal result, including an error; `retry --attempt ID` explicitly retries the saved bytes and settings. A superseded retry can add history but cannot replace a newer revision. |
| OQ-05: refresh | Fingerprint source bytes, provider/model/request settings, prompt, schema and extraction implementation version. Track routing-policy version separately. An extraction fingerprint change schedules a new extraction; a policy-only change reroutes the saved valid extraction without a model call. Retain all prior attempts and provenance. Error records remain eligible for explicit retry; policy refresh does not invent a valid extraction. |
| OQ-06: valid input | Accept UTF-8 JSON objects with a string `message`; ancillary metadata is optional and never supplies business facts. Use the basename as document_id. Reject duplicate basenames within a batch before scheduling ambiguous work. A later batch with that basename is a revision. Invalid encoding/JSON/message becomes a per-document input error, with original-byte hash and actionable diagnostic; other documents continue. Unknown metadata/export versions do not change extraction behavior. |
| OQ-07: pending view | Keep work state (`queued`, `running`, `retry-wait`, `interrupted`, `completed`) separate from policy status. Progress identifies revision, attempt, hash and settings. A refresh marks an older completed result as stale in the operational view until the newer attempt completes; it never labels that old extraction as the new source. Current terminal exports describe completed attempts only, with pending work available separately. |
| OQ-08: validation | Block publication of successful data on bad envelope, refusal/incompletion, invalid JSON/schema, invalid date representation/calendar dates, empty scalar strings, or fabricated supporting quotes. Report an extraction error without automatic repair. Genuine missing/uncertain facts remain null with issues; explicit reversed dates remain as stated and route to clarification. Source-grounded fixtures and accuracy review check unsupported facts beyond these deterministic gates; a quote check alone cannot establish factual correctness. |
| OQ-09: override review | Independently inspect decoded source for explicit instructions to override approval/prompt priority, disclose credentials, or mark approval, in addition to model-reported issues. Preserve exact evidence and an issue; do not obey the instruction. IT-006 anchors acceptance. Plain access requests do not trigger detection. Ambiguous quoted override examples conservatively go to human inspection; document likely false positives and that this is not exhaustive injection detection. |
| OQ-10: workload | Use durable per-document jobs, bounded workers, bounded responses and paginated progress/queue reads. Verify scheduling/storage with 400- and 2,000-message mock batches, slow peers and an outage. These are capacity exercises, not proof of a production latency, quota or cost target; no source establishes one. Expose backlog and failure counts for operators. |

Proposed CLI spelling for later implementation: `python3 -m access_intake intake PATH --provider mock --state PATH`, `queue`, `progress`, `history --document ID`, `retry --attempt ID`, `resume`, `refresh`, `export`, and `accuracy`, all using the same explicit state location. README must supply complete runnable commands and mock-response configuration rather than relying on these shorthand examples. Finite worker leases and attempt-token fencing recover interrupted jobs; no lease expiry permits a stale worker to publish over a replacement attempt.

## 2. Steps, in build order

For each implementation step, first write its owned tests from §3 and observe failure caused by the missing behavior, then implement until they pass. Tests in steps 1–7 call the provider, loader, validator, router or worker-service interfaces directly through a test harness; they do not require the step-8 operator CLI. T29 checks a retry description and injected retry handler; T36 uses worker processes. CLI execution/formatting belongs to T39/T40. A row's case ID names the future unittest method `test_<ID>` (for example `test_T01`), except C01, which is the manual submission check owned by step 10. No test or check belongs to two steps. Later integration tests may exercise earlier components but are first introduced only in their owning step. No step requires a live model call or `API_KEY`; dummy credentials are injected in memory only for adapter tests. Step 10 uses repository and Classroom access under the facilitator's instructions.

### Reading the cases and their sources

Supplied filenames `IT-001.json` through `IT-020.json` below mean the actual exports under `materials/requests/`. All 20 exports were reopened and their decoded `message` strings read during this review; inputs were checked against the message content, not inferred from subjects or filenames. Authored IT-901/IT-902/IT-903 inputs and altered copies are explicitly synthetic, created only in temporary test directories during implementation; they do not currently exist under `materials/requests/`. Keep the supplied exports unchanged. C01 is an artifact/submission check, so it has no message input.

All proposed fixture filenames are relative to `tests/mock_responses/`; none is written now. Each success fixture wraps a complete schema object with a completed provider envelope; refusal/incomplete fixtures exercise envelope handling rather than pretending to be extraction objects. An error may instead be a scripted provider/transport exception. Fixtures are authored independently from the expectations below and never replace the source-derived expected ledger. Tests read expected facts from that ledger, never derive them by copying a measured output or the fixture under test.

Mock cells name full saved-reply paths explicitly. The family `tests/mock_responses/schema/missing-<field>.json` means one future saved reply for each required schema property, substituting its literal name: request_id, request_date, kind, requester, team, system, environment, permission, business_purpose, start_date, end_date, manager, supporting_quotes and issues. Delays replay the named reply after a controllable event; they are not separate unnamed responses. Scripted errors are raised by the fake provider/transport. All tests, including subprocess and README walkthrough checks, run with external network access blocked and API_KEY absent from the caller's environment. T30 creates a distinctive dummy value in its isolated test environment solely to verify environment loading/redaction; no real key is required or used. Its actual adapter implementation receives an injected fake HTTP transport, so it never contacts a provider. C01 is a manual artifact check with no model response.

Business expectations use the message excerpts and policy quotations in their Source cell. When a later row says “T02 facts” or “T03 facts”, it inherits those exact field values and their quoted message/policy sources, not measured outputs. Nulls for absent facts cite the complete named message, the absence of a statement, and the null-with-issues policy; there are no message words to quote for a fact that was never supplied. Operational assertions such as lease fencing, retry bounds and snapshot atomicity cite the operational requirements and the explicitly chosen §1 design rule instead of inventing an office-policy quotation.
